# URL Shortener — Capacity Estimation

This section documents the assumptions and calculations needed to size the first version of the URL Shortener. Capacity estimates are directional: their purpose is to guide architecture choices, not to predict an exact number.

> **Important:** The numbers below are explicitly labelled as examples. Replace them with the agreed product traffic assumptions before making infrastructure commitments.

## Capacity inputs

Define these inputs first:

| Input | Symbol | Example assumption | Notes |
|---|---:|---:|---|
| Daily active users | `DAU` | Not decided | Unique users who use the service per day. |
| URLs created per user per day | `C` | Not decided | Average number of new short URLs per active user. |
| Redirects per created URL per day | `R` | Not decided | Average number of redirects generated by one created short URL. |
| Peak multiplier | `P` | `10x` | Peak requests are assumed to be ten times average requests. |

### Request-volume formulas

```text
URLs created/day = DAU × C
Redirects/day    = URLs created/day × R

Average creation requests/second = URLs created/day / 86,400
Peak creation requests/second    = Average creation requests/second × P

Average redirect requests/second = Redirects/day / 86,400
Peak redirect requests/second    = Average redirect requests/second × P
```

Redirect traffic is normally much larger than creation traffic. This is why the short-code-to-original-URL lookup must be designed as a fast, scalable read path.

# Storage Estimation

Storage estimation answers a practical question: **after running the service for a period of time, how much database capacity will the URL records require?**

## Per-record storage assumption

A URL record may contain the following fields:

| Field | Example | Approximate raw size |
|---|---|---:|
| `id` | `123456789` | 8 bytes |
| `short_code` | `aB72xK9` | ~7 bytes |
| `original_url` | `https://example.com/...` | ~200 bytes |
| `ip_address` | IPv4 or IPv6 address | ~16 bytes |
| `created_at` | timestamp | 8 bytes |
| `deleted_at` | timestamp or `NULL` | up to 8 bytes |

For early capacity planning, do not try to calculate the exact physical row size of a specific database. Instead, use a safe planning estimate that accounts for metadata and row overhead:

```text
Example assumption: one URL record ≈ 500 bytes
```

The final value should be revisited once the database engine, schema, indexes, maximum URL length, and deletion-retention policy are known.

## Storage calculation

Let:

```text
N = URLs created per day
S = estimated bytes per URL record
```

Then:

```text
Raw storage/day  = N × S
Raw storage/year = Raw storage/day × 365
```

### Worked example only

The following is an example calculation, not a product traffic assumption:

```text
URLs created/day (N) = 1,000,000
Storage per URL (S)  = 500 bytes

Raw storage/day
= 1,000,000 × 500 bytes
= 500,000,000 bytes
≈ 500 MB/day

Raw storage/year
= 500 MB/day × 365
≈ 182.5 GB/year
```

With those **example** inputs, the service would store roughly **180 GB of raw URL-record data per year**.

## Raw storage is not total database capacity

The raw-record estimate is only the starting point. Real capacity planning must also allow for:

| Additional capacity | Why it is needed |
|---|---|
| Indexes | The redirect lookup needs an index on `short_code`; listing a user's URLs likely needs an index such as `(ip_address, created_at)`. |
| Database overhead | Rows, pages, metadata, free space, and engine-specific storage overhead consume space. |
| Replication | High availability commonly keeps one or more replicas, each requiring a copy of the data. |
| Backups | Point-in-time recovery and retained snapshots require separate storage. |

Therefore, a raw estimate of `180 GB/year` does **not** mean provisioning exactly `180 GB` of database storage. The production capacity target should include headroom for indexes and database overhead, then separately budget for replicas and backups.

## Design implication for V1

After replacing the example inputs with expected traffic, compare the resulting request rate and storage growth with the limits of the chosen database. At modest scale, a relational database such as PostgreSQL can be a practical V1 choice. As redirect traffic grows, optimize the read path with appropriate indexes and, if needed, caching and read replicas.
